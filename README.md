# Mini GPT — 수학 정리 텍스트 생성

Wikipedia의 수학 정리(Mathematical theorems) 문서들을 코퍼스로 삼아, Transformer 디코더 구조를 처음부터 구현하고 학습시켜 글자 단위(character-level)로 새로운 수학 정리 스타일의 텍스트를 생성하는 프로젝트. 지금까지의 프로젝트들이 전부 "정답을 맞히는" 판별(discriminative) 문제였다면, 이번이 처음으로 다루는 생성(generative) 모델이다.

## 1. 데이터 수집

- Wikipedia API(`wikipedia-api`)로 `Category:Mathematical theorems` 문서 수집. 카테고리 멤버는 실제 문서(ns=0)와 하위 카테고리(ns=14)가 섞여 있음을 확인. 이름이 넓은 카테고리(`Category:Theorems`)는 물리학/게임이론/사회학까지 섞여 부적합함을 확인 후 좁힘.
- 메인 카테고리(54개) + 하위 카테고리 17개까지 1단계 재귀 수집, `set`으로 중복 제거 → 총 1,100개 문서 제목 확보.
- 문서 다운로드 실패 시에도 중단되지 않게 `try/except` 처리, 서버 부담 완화를 위해 요청 간 0.1초 대기.
- 최종 코퍼스: `math_theorems.txt`, 약 20.7MB.

### 환경 설정 트러블슈팅
Python 3.14의 `venv` 생성이 `ensurepip` 단계에서 무한 대기하는 문제 재발(버전 미지정 시 최신 버전 자동 선택이 근본 원인). `setup_env.ps1` 체크리스트 스크립트로 자동화해 재발 방지.

## 2. 데이터 전처리

### 2-1. 수식 렌더링 찌꺼기 제거

Wikipedia API의 `.text`가 MathML 수식을 "화면 렌더링용 낱개 글자 나열" + "원본 LaTeX 소스" 형태로 같이 추출한다는 걸 발견. 정규식으로 제거하는 과정에서 여러 시행착오:

1. `{\displaystyle...}`만 제거 → 10%(과소 제거, 낱개 글자 잔존)
2. "빈 줄 3번 이상 ~ `{\displaystyle}`까지" 넓게 매칭 → 90.28%(과다 제거 — non-greedy 매칭도 시작점이 잘못되면 무의미함을 확인. 흔한 시작 패턴(빈 줄) 때문에 다음 문서 본문까지 삼킴)
3. 줄 단위로 전환, "2칸 이상 들여쓰기로 시작하는 줄" 조건으로 재검증 → 거짓 양성 없음 확인 후 채택
4. 순수 공백/빈 줄이 `\S` 조건에 안 걸려 남는 것 발견 → 연속 압축 시도
5. `\n{3,}`이 줄바꿈 사이 스페이스 때문에 "연속"으로 인식 못해 실패(제거 비율과 실제 샘플 불일치로 발견) → 스페이스 선제거 후 재적용해 해결

최종적으로 원본 대비 71.56% 감소(19.4M자 → 5.5M자). 줄 단위로는 전체의 약 38%가 낱개 글자 줄이었음을 확인해 근거 있는 수치로 판단. 정상 문장 훼손 여부는 여러 지점 샘플링으로 검증 완료.

원본 448종 중 대부분이 외국인 수학자 이름의 원어 표기(한자, 아랍 문자, 키릴 문자 등)나 인코딩 잡음(zero-width space 등). 단순 빈도 threshold만 쓰면 ∃, ∑, ℝ처럼 드물지만 수학적으로 중요한 기호까지 제거되는 문제가 있어, (1) 빈도 필터링, (2) 수동 화이트리스트, (3) 유니코드 카테고리(Sm) 기반 보존을 함께 적용. vocab에 없는 글자는 삭제 대신 UNK(▯)로 치환 — 삭제 시 문장 구조가 훼손되고, 신경망은 애초에 정수만 입력받을 수 있기 때문. 이 UNK 치환까지 반영한 최종 코퍼스를 `math_theorems_final.txt`로 저장(이후 인코딩·학습은 이 파일 기준).

### 2-3. 정수 인코딩 + Train/Val 분리 + 배치 샘플링

| 항목 | 값 |
|---|---|
| 전체 시퀀스 길이 | 5,517,676 |
| train_data 길이 | 4,965,908 (약 90%) |
| val_data 길이 | 551,768 (약 10%) |
| 분리 방식 | 시간 순서 기반 (앞부분=train, 뒷부분=val) |

`stoi`로 전체 텍스트를 정수 텐서로 인코딩 후, `itos`로 되돌려 원문과 일치하는지 왕복 검증. Train/Val 분리는 시계열 프로젝트와 같은 이유(data leakage 방지)로 무작위 셔플 대신 시간 순서 기준 분할.

배치 생성은 모든 슬라이딩 윈도우를 미리 저장하지 않고, 학습 스텝마다 무작위 시작 위치를 뽑아 즉석에서 `block_size`만큼 잘라 쓰는 방식(`get_batch`). 전체 코퍼스가 모든 윈도우를 미리 저장하기엔 너무 크고, 텍스트 생성 모델은 문맥 길이 1~block_size 전체에서 예측 가능해야 하므로, 하나의 윈도우 안에서도 여러 개의 (X, y) 쌍을 동시에 학습에 활용한다는 점이 시계열의 "윈도우당 정답 1개" 방식과 다르다.

## 3. 모델 구조: Self-Attention → Multi-Head → Block → GPTModel

Self-Attention 한 조각(Q/K/V → 관련성 점수 → causal masking → softmax → value 가중합)을 재사용 가능한 부품으로 조립.

- **`Head`**: `nn.Module`로 캡슐화. `tril`(미래 마스킹용 하삼각행렬)은 학습 대상이 아니므로 `nn.Parameter` 대신 `register_buffer`로 등록.
- **스케일링(`1/√head_size`)**: 서로 독립인 항 n개를 더하면 분산은 n배(표준편차는 √n배)가 됨을 직접 유도. `head_size`가 아니라 표준편차 기준인 `√head_size`로 나눠야 원래 분산(1)로 정확히 되돌아옴을 확인.
- **`MultiHeadAttention`**: `Head`를 `nn.ModuleList`로 병렬 배치(`num_heads × head_size = n_embd`로 파라미터 총량 유지). 각 head는 서로 다른 독립 가중치로 같은 입력 전체를 각자 다른 기준으로 훑고, Softmax는 head마다 독립 계산됨(`head_size` 축이 아니라 문맥 길이(T) 축에서 계산)을 확인.
- **`FeedForward`**: `n_embd → 4·n_embd → n_embd`로 일시 확장 후 압축. 좁은 차원에서 바로 변환하는 것보다 넓은 중간 공간에서 ReLU가 더 다양한 조합을 탐색한 뒤 압축하는 쪽이 표현력이 높음.
- **`Block`(잔차 연결 + LayerNorm)**: `x = x + sa(ln1(x))`, `x = x + ffwd(ln2(x))`. 잔차 연결을 LSTM의 Constant Error Carousel과 같은 원리로 이해 — `d(x+f(x))/dx = 1+f'(x)`이므로 `f'(x)`가 아무리 작아져도 "+1"이라는 바닥값이 항상 보장되어 기울기 소실을 방지. LayerNorm은 각 토큰 벡터 안에서 평균0/분산1로 정규화한 뒤, 학습 가능한 `γ`(스케일)·`β`(이동)로 표현력을 되돌려주는 구조(`ln1`, `ln2`는 서로 다른 `γ/β`를 학습하도록 독립 인스턴스로 분리).
- **`GPTModel`**: 토큰 임베딩+위치 임베딩 → `nn.Sequential(*[Block(...) for _ in range(n_layer)])`로 n개 Block을 쌓음(`*`로 리스트를 개별 인자로 언패킹) → 최종 LayerNorm → `nn.Linear(n_embd, vocab_size)` 출력층. `targets=None`이면 loss를 계산하지 않는 분기를 둬 생성 단계에서 재사용 가능하도록 설계. Loss 계산 전 `logits.view(B*T, C)`로 배치×시퀀스 축을 하나로 펼쳐, 각 위치의 다음 글자 예측을 B×T개의 독립된 분류 문제로 변환.
- **디버깅 사례**: `x = self.ln_f(x)`를 `x - self.ln_f(x)`로 오타 냈는데도 에러 없이 실행됨을 발견 — 대입(`=`)과 뺄셈(`-`)이 둘 다 문법적으로 유효해, 최종 LayerNorm이 적용되지 않은 채로 조용히 학습되고 있었음.

## 4. 학습 루프

- **AdamW**: 전통적 Adam+L2 decay는 weight decay가 `√v_t`(2차 모멘텀) 나눗셈에 휘말려 파라미터/학습 단계별로 decay 세기가 왜곡되는 문제가 있음. AdamW는 decay(`λ·θ`)를 나눗셈 바깥에서 별도로 적용해(decoupled), 가중치 크기에만 정확히 비례하도록 분리.
- **초기화 직후 loss 검증**: 무작위 초기화 상태에서 20회 평균 loss(6.40, 표준편차 0.19)가 이론적 바닥값 `log(vocab_size)=log(294)=5.68`보다 살짝 위에서 안정적으로 형성됨을 확인. `-log(p)`가 정답 확률이 낮을 때 더 가파르게 커지는 특성상, 무작위 초기화는 완전 균등분포보다 항상 약간 높은 loss를 보이는 것이 정상.
- **`estimate_loss()`**: `@torch.no_grad()` + `model.eval()/train()`으로 train/val 각각 50개 배치 평균을 주기적으로 측정. train_loss만으로 판단하지 않고 val_loss를 항상 같이 확인.

## 5. 모델 용량 실험: n_embd / n_layer / block_size 비교

| 조합 | n_embd | n_layer | block_size | final train loss | final val loss |
|---|---|---|---|---|---|
| ① baseline | 16 | 4 | 8 | 2.3924 | 2.3838 |
| ② 깊이만 증가 | 16 | 6 | 8 | 2.4012 | 2.3927 |
| ③ 폭만 증가 | 64 | 4 | 8 | 2.0320 | 2.0396 |
| ④ 폭+깊이 | 64 | 6 | 8 | 1.9456 | 1.9805 |
| ⑤ 문맥 2배 | 64 | 6 | 16 | 1.7540 | 1.8072 |
| ⑥ 문맥 4배 | 64 | 6 | 32 | 1.6322 | 1.6688 |
| ⑦ 문맥 8배 | 64 | 6 | 64 | 1.6286 | 1.6373 |

(모두 16000스텝, 동일 조건 1회 실행 기준)

- **깊이(`n_layer`) 단독 증가는 거의 무효**(①→②, val 기준 +0.009). Fashion-MNIST·house-price-regressor에서 "최적 구조는 데이터 성격에 따라 다르다"를 확인했었는데, 표 데이터에서는 깊이가 폭보다 유리했던 것과 반대로 이 문제는 폭이 훨씬 중요.
- **폭(`n_embd`) 증가는 뚜렷한 효과**(①→③, val -0.344).
- **문맥 길이(`block_size`)가 가장 큰 병목**: 8→16→32로 2배씩 늘릴 때마다 val loss가 각각 -0.173, -0.138 감소해 n_embd 4배 증가 효과(-0.344)에 필적하거나 상회. 32→64 구간은 개선폭이 -0.032로 급격히 줄어(직전 두 구간의 1/4 이하), 계산 비용(4배 증가) 대비 효율이 크게 나빠지는 수확체감 지점에 도달.
- **과적합 신호 없음**: 7개 조합 전부 train/val이 끝까지 벌어지지 않음(가장 큰 모델도 최종 차이 0.009) — 데이터(5.5M자) 대비 시도한 모델 크기들은 전부 과소적합 쪽에 더 가까웠던 것으로 판단.

### 최종 모델 확정

비용 대비 효율을 고려해 `n_embd=64, n_layer=6, block_size=32`(⑥번 조합)를 최종 채택. 동일 설정 재학습 결과 `train 1.7105, val 1.7097`로 실험값(1.6322/1.6688)과 근소한 차이 — 무작위 초기화·배치 샘플링에 따른 정상적인 변동 범위로 판단(1회 실행 기준, 엄밀한 반복검증은 하지 않음). 가중치는 `gpt_model.pt`(state_dict), 설정은 `gpt_config.json`으로 저장해 재현 가능하도록 함.

## 6. 생성(Sampling)

자기회귀적(autoregressive) 생성: 현재까지의 시퀀스를 최근 `block_size`개로 잘라(`idx[:, -block_size:]`) 모델에 넣고, 마지막 위치의 예측 확률 분포(`logits[:, -1, :]` → softmax)에서 `torch.multinomial`로 다음 글자 하나를 확률적으로 뽑아 이어붙이는 과정을 반복. `argmax` 대신 `multinomial`을 쓴 이유는, 모델이 계산한 확률 분포 전체(낮은 확률의 다른 가능성까지)를 존중해 매번 다양한 텍스트를 생성하기 위함.

**디버깅 사례**: `idx[:, -block_size:]`를 `idx[:-block_size:]`(콤마 누락)로 잘못 적어, "시퀀스 축을 자르기"가 아니라 "배치 축을 자르기"로 동작이 완전히 바뀌어버림. 배치 크기가 1이었던 탓에 결과가 크기 0인 빈 텐서가 되어 `torch.cat`에서 에러 발생. 콤마 하나가 "몇 번째 축에 규칙을 적용할지"를 결정한다는 점을 실제 버그로 확인.

### 생성 결과와 정성적 한계

`start_char="T"`로 5회 반복 생성한 결과, 같은 시작 글자에서도 매번 다른 텍스트가 나와 `torch.multinomial` 기반 확률적 샘플링이 의도대로 작동함을 확인했다(`argmax`를 썼다면 5회 모두 동일한 텍스트가 나왔을 것).

**잘 포착된 패턴**: `proof`, `theorem`, `elements`, `subset`, `identities`, `Topological proof`, `Theorem, such that`처럼 실제 수학 어휘·정리 진술의 관용구가 형태를 갖춰 등장. 대문자 시작, 마침표/콜론/줄바꿈 배치도 실제 텍스트의 리듬을 어느 정도 재현.

**해석 불가능한 조합**: `woundavet`, `drucibolog`, `arzttiR`, `Cortgradicianchs`, `agmatixic`, `apclocin`처럼 영어 단어도, 수학 용어도 아닌 글자 조합이 다수 등장.

이는 실패라기보다 글자 단위(character-level) 모델의 본질적 한계로 해석했다. 이 모델은 "단어"나 "문법"이라는 단위를 명시적으로 학습한 적이 없고, 오직 "이 글자 다음에 어떤 글자가 올 확률이 높은가"만 학습했다. `proof`, `theorem`처럼 코퍼스에 자주 등장한 단어는 그 글자 순서 패턴 자체를 강하게 학습해 재현할 수 있지만, 철자 규칙이나 형태소 단위의 제약이 없다 보니 학습 빈도가 낮은 조합에서는 존재하지 않는 글자열을 그럴듯한 위치에 만들어낸다. 감성분석 프로젝트에서 BoW가 단어 순서 정보를 모른다는 한계를 확인했던 것과 같은 결의 문제 — "다음 단위를 예측한다"는 목표가 그보다 상위 단위(단어/문법)의 규칙성을 보장하지 않는다는 한계다.

## 7. Subword 토큰화(BPE) 직접 구현 및 비교

글자 단위 모델의 한계(존재하지 않는 단어 생성)를 완화할 수 있는지 확인하기 위해, BPE(Byte Pair Encoding)를 라이브러리 없이 직접 구현했다.

### BPE 알고리즘 구현

- **원리**: 단어를 글자 단위로 쪼갠 뒤(`</w>`로 단어 경계 표시), 인접한 두 토큰 중 코퍼스 전체에서 가장 흔한 쌍을 찾아 하나로 병합하는 과정을 반복. 매 병합은 정확히 두 토큰만 묶으며, 3글자 이상의 조각은 여러 라운드에 걸쳐 누적적으로 형성됨(예: `(t,h)`→`th`, 다음 라운드에 `(th,e)`→`the`).
- **`</w>`(단어 경계 표시)가 필요한 이유**: 이게 없으면 서로 다른 두 단어가 우연히 이웃했다는 이유만으로 그 경계를 걸친 글자 조합이 병합 후보로 잘못 섞여 들어갈 수 있음.
- **탐욕적(greedy) 알고리즘의 한계**: 한 번 병합되면 되돌리지 않음. 예를 들어 `(b,c)`가 이번 라운드 1등으로 병합되면, 그 단어 안에서 `(c,d)`는 이후 영구히 병합 기회를 잃음 — K-means의 local minimum과 같은 계열의 한계.
- **`word_freq` 사전 집계 및 캐싱**: 같은 단어를 반복 계산하지 않도록, 처음 등장한 단어만 실제로 토큰화 계산을 하고 이후엔 캐시에서 재사용(`the`가 53,711번 등장해도 실제 계산은 1회).
- **vocab_size의 정확한 의미**: "단어 종류 수"가 아니라 "고유 토큰(글자+병합된 조각) 종류 수" — 병합마다 새 토큰이 1개씩 추가되며 기존 토큰은 사라지지 않음(다른 단어에서 낱개로 계속 쓰일 수 있음). 500번 병합 후 실제로 초기 글자 287종이 전부 vocab에 남아있음을 `set` 차집합으로 직접 검증.
- **미지의 단어 대응력 검증**: 코퍼스에 없는 임의의 단어(`xyzzyplugh`)를 토큰화했을 때, 학습된 조각(`pl`)과 낱개 글자로 쪼개져서라도 표현 가능함을 확인(완전한 단어 단위 vocab이었다면 표현 불가능했을 상황).

### vocab 구축 결과

| 항목 | 값 |
|---|---|
| 고유 단어 수 | 65,990 |
| 병합 횟수 | 500 |
| 최종 vocab_size | 787 |
| 전체 코퍼스 토큰 수 | 2,216,063 (글자 단위 5,517,676 대비 59.85% 압축) |

### 모델 재학습 (n_embd=64, n_layer=6, block_size=32, vocab_size=787)

글자 단위 최종 설정을 그대로 유지하되 vocab_size만 787로 교체. GPU(CUDA) 학습으로 전환(`.to(device)`, `torch.arange`에 `device` 명시 필요 — 누락 시 `index_select` device mismatch 에러 발생).

- **수렴 확인(49,600스텝)**: val loss가 약 35,000~40,000스텝 이후 3.2~3.3대에서 정체 — 초반 두 구간(0→10k, 10k→25k) 대비 개선 속도가 뚜렷이 느려짐.
- **과적합 정량 검증(32,000스텝, 80회 측정)**: train-val 격차를 초반/후반 절반으로 나눠 SE 비교 — 초반 평균 0.0440(SE 0.0089) vs 후반 평균 0.0878(SE 0.0098), 차이가 SE 합의 약 2.4배로 통계적으로 유의미한 증가. 다만 절대 크기는 작아(약 0.09) 심각한 과적합은 아님 — "이 모델 용량 대비 32,000스텝이 다소 과함" 정도로 해석.

### 글자 단위 모델과의 공정한 비교 — loss 환산

BPE와 글자 단위는 클래스 수(787 vs 294)와 예측 단위(서브워드 조각 vs 글자)가 달라 loss를 직접 비교할 수 없음. "코퍼스 전체 글자 수 ÷ 토큰 수" 비율을 글자당 loss로 환산하는 배율로 사용.

- **비율의 안정성 검증**: val 구간을 10등분해 각 조각의 글자/토큰 비율을 독립 계산 — 평균 2.4907, 표준편차 0.0811(변동계수 약 3.3%)로 안정적임을 확인(초기 우려와 달리 편중된 단어 분포의 영향이 크지 않았음).
- **환산 결과**: BPE val loss 3.3905(32,000스텝 기준) ÷ 2.4907 ≈ 1.3612 — 글자 단위 모델의 최종 val loss(1.6688)보다 낮음. 같은 정보량 기준으로 BPE가 유리했을 가능성을 시사.

### 생성 결과 비교

동일하게 확률적 샘플링(`torch.multinomial`)으로 생성. BPE 디코딩은 `</w>`를 공백으로 치환하는 과정이 추가로 필요.

- **개선된 부분**: `determinator`, `infinitables`, `treatable`, `distribution`, `Hermite`처럼 실제 영어 형태소 규칙을 따르는 단어가 크게 늘어, 글자 단위 모델의 "존재하지 않는 단어 생성" 문제가 뚜렷이 완화됨.
- **여전한 한계**: 단어 내부 철자는 개선됐지만, 문장 수준의 문법·의미 구조는 여전히 무너짐(`"The determinator m hold all infinitables"`). `Remanning–Riophis`, `Hermorhelms`처럼 실존하지 않는 고유명사도 계속 생성됨 — BPE가 해결하는 층위(단어 내부 규칙)와, 아직 해결 안 된 층위(단어 간 문법)가 다르다는 것을 확인.

## 8. 샘플링 전략 비교: top-k / top-p vs 순수 multinomial

순수 `multinomial`은 787개 전체 확률분포에서 샘플링하다 보니, 확률이 극히 낮은 후보(긴 꼬리)가 가끔 뽑혀 `Remanning–Riophis` 같은 붕괴된 조합의 원인이 되는 것으로 추정. 후보를 미리 좁히는 top-k(상위 k개만 남김), top-p(누적확률 p까지만 남김, nucleus sampling)를 직접 구현해 비교.

### 평가 지표 설계

- **실존 단어 비율**: 생성된 각 단어(구두점 제거 후)가 학습 코퍼스의 `word_freq`(65,990개 고유 단어)에 실제로 등장했는지 비율로 측정. 시작 단어 5개(`The, Let, If, Suppose, For`) × 5회 반복 = 방식당 25회 생성으로 평균/SE 산출.
- **다양성**: 같은 시작 단어(`"The"`)로 5회 생성한 결과들을 단어 집합으로 변환해, 모든 쌍(10개 조합)의 Jaccard 거리(`1 - 교집합/합집합`)를 평균. 값이 클수록 반복 생성 시 서로 다른 텍스트가 나온다는 뜻.

### 결과

| 방식 | 실존 단어 비율 | 다양성 |
|---|---|---|
| 기존 (순수 multinomial) | 0.7074 | 0.9212 |
| top-k=5 | 0.8956 | 0.8197 |
| top-k=10 | 0.8665 | 0.8408 |
| top-k=20 | 0.8200 | 0.8322 |
| top-k=30 | 0.8134 | 0.8925 |
| top-p=0.7 | 0.8530 | 0.8542 |
| top-p=0.8 | 0.8468 | 0.8690 |
| top-p=0.9 | 0.7776 | 0.8694 |
| top-p=0.95 | 0.7788 | 0.9167 |

- **명확한 트레이드오프 확인**: 후보를 좁게 자를수록(k, p가 작을수록) 실존 단어 비율은 오르고 다양성은 대체로 내려감. 기존 방식이 다양성 최고점(0.9212)이자 실존 단어 비율 최저점(0.7074)으로, 정확히 트레이드오프의 한쪽 극단에 위치.
- **top-k=10 vs 기존, SE 검증**: 차이 0.1591이 SE 합(0.0338)의 약 4.7배로 뚜렷하게 유의미 — top-k 방식 자체가 순수 multinomial보다 낫다는 결론은 신뢰할 수 있음.
- **균형점**: 두 지표를 함께 고려하면 k=10, p=0.8 정도가 실존 단어 비율과 다양성 모두 준수한 균형점으로 판단.

### 다양성 지표 재검증 (독립 샘플 25개 기준)

최초 측정은 같은 시작 단어(`"The"`)로 5회만 생성해 쌍 10개를 만든 값이었는데, 이 10개는 텍스트 5개가 겹쳐 쓰이며 서로 의존적이라(한 텍스트가 특이하면 그 텍스트가 낀 쌍 4개가 동시에 흔들림) SE를 낼 수 있는 "독립 샘플"이 아니었다. 이를 보완하기 위해 "시작 단어 5개(`The, Let, If, Suppose, For`) × 각 5회 반복"으로 다양성 값 자체를 25번 독립적으로 재계산(매번 텍스트 5개 생성 → 쌍 10개 평균 → 다양성 값 1개)했다.

| 방식 | 다양성 평균 (n=25) | SE |
|---|---|---|
| 기존 (순수 multinomial) | 0.9139 | 0.0026 |
| top-k=5 | 0.8087 | 0.0034 |
| top-k=10 | 0.8406 | 0.0036 |
| top-k=20 | 0.8630 | 0.0036 |
| top-k=30 | 0.8748 | 0.0039 |
| top-p=0.7 | 0.8839 | 0.0035 |
| top-p=0.8 | 0.8908 | 0.0022 |
| top-p=0.9 | 0.9072 | 0.0033 |
| top-p=0.95 | 0.9061 | 0.0029 |

- **이전에 봤던 역전 현상(k=20 < k=10)은 노이즈였음이 확인됨**: 25개 샘플로 재측정하니 k=5→10→20→30으로 갈수록 다양성이 일관되게 증가. k=10(0.8406) vs k=20(0.8630) 차이(0.0224)가 SE 합(0.0072)의 약 3.1배로, 이번엔 "k가 클수록 다양성도 커진다"가 통계적으로 뚜렷한 패턴임을 확인.
- **top-p=0.9와 0.95 사이는 여전히 순서가 뒤집혀 있지만(0.9072 vs 0.9061), 이번엔 노이즈로 판단 가능**: 차이(0.0011)가 SE 합(0.0062)의 0.18배에 불과해 사실상 구분 불가능한 차이. top-k 계열의 뚜렷한 단조 증가와 달리, top-p는 p=0.9 이상 구간에서 다양성이 사실상 평평해지는 것으로 해석.
- **표본을 5배 늘리자(5회→25회) SE 자체도 절반 이하로 작아짐**(예: 0.0338 수준의 흔들림이 있던 것이 0.002~0.004대로 촘촘해짐) — 표본 크기가 작을 때 나온 비선형적 패턴을 성급히 실제 현상으로 해석하면 안 된다는 원칙이 여기서도 재확인됨.

## 9. BPE 병합 횟수 실험 (500 vs 1,000 vs 2,000)

기존 BPE는 병합을 500번 해서 vocab_size=787을 만들었는데, 병합 횟수를 늘리면 vocab_size는 커지는 대신 시퀀스가 더 짧게 압축된다는 트레이드오프가 있다. 이 트레이드오프가 실제 압축률과 loss에 어떻게 나타나는지 확인했다.

### 9-1. vocab 구축 단계 (재학습 없이 압축률만 비교)

| 병합 횟수 | vocab_size | 압축률 (글자/토큰) |
|---|---|---|
| 500 | 787 | 2.490 |
| 1,000 | 1,287 | 2.946 |
| 2,000 | 2,282 | 3.498 |

- **병합 1번당 압축 개선 효과는 수확체감**: 500→1,000 구간은 병합 1번당 +0.000912, 1,000→2,000 구간은 +0.000552로 약 40% 감소. `get_pair_freqs`에서 매번 가장 빈도 높은 쌍부터 병합하는 탐욕(greedy) 방식이라, 흔한 쌍은 초반에 먼저 소진되고 후반으로 갈수록 남은 후보의 빈도 자체가 낮아지는 게 원인.

### 9-2. 재학습 후 loss 비교 (32,000 스텝, 각 2회 반복)

| vocab | 글자당 val loss (평균, n=2) | SE |
|---|---|---|
| 500 (vocab_size=787) | 1.3503 | 0.0015 |
| 1,000 (vocab_size=1,287) | 1.3223 | 0.0131 |
| 2,000 (vocab_size=2,282) | 1.2860 | 0.0055 |

- **토큰당 loss만 보면 정반대 결론**: vocab이 커질수록(787→1287→2282) 토큰당 val loss는 오히려 계속 나빠짐(3.33→3.90→4.51). 이는 비교 대상 개수가 늘어나 "찍었을 때 맞을 확률"의 기준선 자체가 낮아지는 착시(예: `-log(1/787)` vs `-log(1/2282)`는 시작부터 다름)와, 토큰 하나가 담는 정보량(글자 수)이 vocab마다 다르다는 사실이 뒤섞인 결과.
- **글자당 loss(= 토큰당 loss ÷ 압축률)로 환산하면 방향이 뒤집힘**: vocab이 커질수록 오히려 개선(1.3503→1.3223→1.2860). 토큰당 loss는 "비교 난이도"와 "정보 압축량" 두 가지가 섞인 지표라, 공정한 비교를 위해선 같은 단위(글자)로 환산이 필요하다는 걸 실증.
- **SE로 검증한 결과, 결론의 확실성은 구간마다 다름**: 500 vs 2,000(극단 비교)은 차이가 SE 합의 약 9.2배로 뚜렷하게 유의미. 반면 인접 구간(500 vs 1,000: 1.9배, 1,000 vs 2,000: 1.95배)은 2배 문턱 근처라 "진짜 단계적으로 개선되는지"는 n=2로는 확정하기 어려움 — 특히 1,000 지점의 SE(0.0131)가 다른 두 지점보다 훨씬 커서, 표본 2개짜리 표준편차 추정의 불안정성이 그대로 드러남.

### 9-3. 이번 실험에서 겪은 디버깅 사례

- **죽은 코드가 정답을 덮어씀**: 체크포인트별 vocab을 "라이브 vocab에서 직접 추출"하는 방식으로 고쳤는데도, 그 이전에 짜뒀던 부정확한 "조립 방식"(merges 쌍을 전부 이어붙여 합집합) 코드를 지우지 않고 남겨둬서, 정확한 값 위에 부정확한 값이 다시 덮어씌워짐. 두 버전의 최종 출력이 우연히 똑같이 나와서(789, 1289, 2289) 처음엔 "재조립이 잘 됐다"고 착각했으나, 실제로는 검증용으로 저장해둔 `vocab_size_cp`(원본 병합 루프에서 직접 잰 정답)와 비교해보니 불일치가 드러남. → 리팩토링 시 이전 코드 조각을 완전히 지우지 않으면, 문법 오류 없이 조용히 결과를 오염시킬 수 있음.
- **CUDA 에러의 비동기 특성**: vocab_size가 안 맞는 데이터로 임베딩 조회를 시도해 GPU 컨텍스트가 손상된 뒤, 그와 무관해 보이는 다음 CUDA 호출(`model.to(device)`)에서야 에러가 터짐. CUDA 에러는 발생 시점과 보고 시점이 다를 수 있어(비동기 실행), 에러가 난 줄이 아니라 그 이전 셀들을 의심해야 하며, 한번 터지면 커널을 재시작해야 GPU 상태가 정상으로 복구됨.

## 10. n_head 비교 실험 (2 / 4 / 8 / 16)

`n_embd=64`는 고정한 채, 이를 몇 개의 head로 나눌지(`n_head`)만 바꿔 비교했다. `head_size = n_embd / n_head` 관계상 head를 늘릴수록 개별 head의 표현력(head_size)은 줄어드는 트레이드오프가 있다.

| n_head | head_size | 글자당 val loss (평균, n=4) | SE |
|---|---|---|---|
| 2 | 32 | 3.3578 | 0.0251 |
| 4 | 16 | 3.3284 | 0.0268 |
| 8 | 8 | 3.3710 | 0.0262 |
| 16 | 4 | 3.3928 | 0.0133 |

(vocab_size=787, n_embd=64, n_layer=6, block_size=32, 32,000스텝, 각 4회 반복)

- **2~8 구간은 서로 뚜렷하게 구별되지 않음**: 4가 평균은 가장 낮지만, 4 vs 8 차이(0.0426)가 SE 합(0.0530)보다 작아 노이즈 수준. block_size가 확실한 병목이었던 것과 달리, 이 범위 안에서는 n_head가 val loss에 뚜렷한 영향을 주지 않는다.
- **n_head=16은 확실히 불리함**: 4 vs 16 차이(0.0644)가 SE 합(0.0401)의 약 1.6배로, 우연이 아니라고 볼 만한 차이. head_size가 4까지 좁아지면서 개별 head가 담을 수 있는 정보량 자체가 부족해진 것으로 해석. 2 vs 16(차이 0.0351, SE 합 0.0384)은 아슬아슬하게 노이즈 범위.
- **결론**: 일정 범위 안에서는 head 개수보다 총 표현력(`n_embd`)이 더 중요하고, head_size가 지나치게 좁아지는 극단(16)에서만 손해가 뚜렷해짐 — "최적값 하나를 찾는다"기보다 "너무 극단으로 가지만 않으면 무난한 범위가 있다"는, 지금까지와는 조금 다른 결의 결론.

## 11. 종합 정리

| 구분 | 핵심 발견 |
|---|---|
| 전처리 | 정규식 기반 노이즈 제거는 "제거 비율"만으로 검증하지 말고 실제 샘플로 확인해야 함(과다/과소 제거 모두 숫자로는 안 드러날 수 있음) |
| 모델 구조 | Self-Attention, 잔차 연결, LayerNorm 모두 "왜 필요한가"가 이전 프로젝트(코사인 유사도, LSTM의 CEC, 표준화)의 개념과 직접 연결됨 |
| 용량 실험 | 이 문제(글자 단위 텍스트 생성)에서는 깊이보다 폭이, 그리고 그 무엇보다 문맥 길이(block_size)가 병목이었음 — "최적 구조는 문제 성격에 따라 다르다"는 원칙이 새로운 축(문맥 길이)에서도 재확인됨 |
| 생성 | 확률적 샘플링이 의도대로 작동함을 반복 생성으로 검증. 글자 단위 모델은 단어/문법의 상위 규칙성을 보장하지 못한다는 근본적 한계가 정성적 분석으로 드러남 |
| BPE | 직접 구현한 병합 알고리즘이 압축(약 60%)과 글자당 loss 개선(1.67→1.36) 양쪽에서 효과 확인. 단어 내부 규칙성 문제는 완화됐지만, 문장 수준 문법이라는 다른 층위의 한계는 그대로 남음 — "한 기법이 해결하는 문제의 층위를 정확히 구분해야 한다"는 교훈 |
| 샘플링 전략 | top-k/top-p가 순수 multinomial보다 실존 단어 비율을 통계적으로 유의미하게 높임. 다만 "정확도 vs 다양성"이라는 새로운 트레이드오프가 존재 — 지표 하나만 보고 극단으로 밀어붙이면 안 된다는 원칙이 여기서도 재확인됨 |
| 다양성 재검증 | 5회 반복(쌍 10개, 서로 의존적)만으로 측정했을 때 보였던 역전 현상(k=20<k=10)이, 25개 독립 샘플로 재검증하니 사라짐 — 표본이 작을 때 나온 비선형 패턴을 성급히 실제 현상으로 해석하면 안 된다는 원칙이 재확인됨 |
| BPE 병합 횟수 | 토큰당 loss만 보면 vocab이 커질수록 나빠지는 것처럼 보이지만, 글자당 loss로 환산하면 정반대로 개선됨 — 지표의 "단위"가 비교 대상마다 다른 의미를 가질 수 있다는 것, 그리고 SE로 검증하니 극단 비교(500 vs 2000)는 뚜렷했지만 인접 구간은 n=2로 확정하기 어려운 경계선이었음 |
| n_head 비교 | head 개수(2~8)보다 총 표현력(n_embd)이 더 중요했고, head_size가 지나치게 좁아지는 극단(16)에서만 손해가 뚜렷했음 — 모든 축이 "많을수록/적을수록 좋다"는 단조 관계는 아니라는 사례 추가 |

## 12. 다음에 해보고 싶은 것

- **block_size 추가 탐색**: 32→64 구간에서 수확체감이 보였지만, 128까지는 아직 확인 안 함 — 진짜 한계점이 어디인지 (BPE 기준으로도 재탐색 가능)
- **BPE 병합 횟수 실험 심화**: 1,000~2,000 인접 구간의 방향성이 n=2로는 확정이 어려웠으니, 반복 횟수를 늘리거나(계산 여건이 되면) 더 넓은 범위(예: 4,000)로 확장해 경향을 재검증
- **정성적 오분류(오생성) 사례를 더 체계적으로 수집**: 글자 단위·BPE 각각 더 많은 샘플에서 "해석 불가능한 조합"의 발생 위치나 패턴(예: 특정 글자 조합 이후에 자주 무너지는지) 분석
- **문장 수준 문법 개선 방향 탐색**: top-k/top-p로도 못 잡은 단어 간 문법 오류(`"The determinator m hold"`)를 어떤 방식(더 큰 block_size, 더 많은 학습 데이터, 다른 아키텍처)으로 줄일 수 있을지
